# parentcontrol — спецификация и план реализации

Документ самодостаточен: он описывает, что нужно построить, какие решения уже приняты и в каком порядке работать. Репозиторий на момент написания пуст (нет кода, нет git).

Язык: код, идентификаторы, комментарии и сообщения коммитов — на английском. Интерфейс панели и трея — на русском.

---

## 1. Цель

Родитель хочет ограничить время, которое ребёнок проводит в Minecraft (и в других выбранных программах) на домашних компьютерах под Linux и Windows. Время общее на все компьютеры. Управление — через веб-панель в домашней сети.

## 2. Исходные условия

- **Ребёнок один.** На каждом ПК у него отдельная учётная запись ОС без прав администратора и без sudo.
- **Ребёнок пытливый.** Он будет искать обходы: переименует `java.exe`, поставит другой лаунчер, сменит часовой пояс, выдернет сетевой кабель, убьёт процессы в своей сессии. Прав администратора у него нет, и защита опирается на это.
- **Компьютеров несколько**, на Linux и на Windows. Основной Linux-дистрибутив — NixOS, но решение не должно быть к нему привязано.
- **Minecraft — Java Edition**, запускается через официальный лаунчер или Prism Launcher.
- **Домашний сервер** под Linux работает круглосуточно по адресу `192.168.1.135`. Серверная часть разворачивается там в Docker Compose под пользователем `quantick` (см. 5.7). Детские ПК из дома не выносятся.
- Родители пользуются теми же ПК под своими учётными записями, и их ограничивать нельзя.

## 3. Функциональные требования

### 3.1. Что ограничивается

- Ограничиваются только явно выбранные программы; всё остальное свободно (модель чёрного списка).
- Программы объединяются в **группы** (например, «Игры»: Minecraft и ещё что-то). Квота и расписание задаются на группу. Группа из одной программы — это лимит на программу.
- Программа описывается **правилами**:
  - встроенный профиль (в первой версии один: «Minecraft Java»);
  - своё правило: имя исполняемого файла, путь (glob), подстрока или регулярное выражение по командной строке.
- Ограничения действуют только на процессы, принадлежащие привязанным учётным записям ОС (см. 3.5).

### 3.2. Правила времени

- **Дневная квота** в минутах, отдельно для каждого дня недели.
- **Окна разрешённого времени** для каждого дня недели (например, 16:00–20:00). Вне окна запуск запрещён, даже если квота осталась.
- **Ручная корректировка**: родитель добавляет или забирает N минут сегодняшней квоты группы либо задаёт, сколько осталось на сегодня.
- **Ручная блокировка**: родитель немедленно запрещает группу; действует, пока он её не снимет.
- Играть можно, когда одновременно: остаток квоты больше нуля, сейчас внутри окна, блокировки нет.

### 3.3. Учёт времени

- Время идёт, пока жив хотя бы один процесс группы. Свёрнутое окно и пауза в игре не останавливают счёт.
- Несколько процессов одной группы на одном ПК считаются один раз.
- Одновременная игра на двух ПК тратит бюджет вдвое быстрее (сумма по машинам).
- **Бюджетные сутки начинаются в 04:00** по часовому поясу сервера. Квота дня недели определяется датой начала бюджетных суток. Окна задаются внутри бюджетных суток: окно может пересекать полночь, но не 04:00.
- Время сна компьютера не считается (см. 5.2).

### 3.4. Что происходит при исчерпании

- Уведомления ребёнку за 10, 5 и 1 минуту до ближайшего из событий: конец квоты или конец окна.
- Затем мягкое закрытие (игра должна успеть сохранить мир); через 30 секунд — принудительное завершение.
- Если за эти 30 секунд родитель добавил бонус или снял причину запрета, закрытие отменяется.
- Запуск программы, когда играть нельзя: процесс завершается сразу, ребёнок получает уведомление с причиной (квота кончилась / вне окна / заблокировано родителем).

### 3.5. Привязка к пользователям ОС

- На сервере есть **профиль ребёнка**; к нему относятся группы, квоты и расписание.
- К профилю привязываются учётные записи ОС в виде пар «устройство + имя пользователя». Имена на разных ПК могут отличаться; бюджет общий.
- Агент присылает список локальных пользователей, родитель выбирает нужного в панели из списка.
- Пока на устройстве нет ни одной привязки, агент ничего не ограничивает, а панель показывает устройство как «не настроено».
- Модель данных допускает несколько профилей. Интерфейс первой версии делается под один.

### 3.6. Интерфейс ребёнка

- Системные уведомления (предупреждения и причина закрытия).
- Иконка в трее: остаток по каждой группе и время ближайшего окна.
  - Linux: протокол StatusNotifierItem (в KDE работает сразу, в GNOME нужно расширение). Где трея нет, остаются только уведомления.
- Трей ничего не решает и ничем не управляет. Его завершение не влияет на ограничения.

### 3.7. Веб-панель родителя

Доступна только из домашней сети, удобна с телефона. Разделы:

- **Главная**: остаток на сегодня по группам; кто играет сейчас и на каком ПК; состояние устройств; быстрые действия «+15 / +30 / +60 минут», «заблокировать / разблокировать».
- **Группы и правила**: создание групп, добавление встроенного профиля и своих правил.
- **Расписание**: квота и окна по дням недели для каждой группы.
- **Устройства**: подключение нового ПК, привязка пользователей ОС, время последней связи. Устройство, которое давно не выходило на связь, явно выделено.
- **История**: использование по дням, группам и устройствам; сеансы игры; отметки перерасхода из-за офлайна; журнал действий родителя (корректировки времени, блокировки).
- **Настройки**: пароль, часовой пояс, время начала бюджетных суток.

### 3.8. Работа без связи с сервером

- Агент продолжает ограничивать по последнему известному состоянию: правила, расписание на всю неделю и остаток на момент последней синхронизации минус локально насчитанное.
- Насчитанное хранится в локальном журнале и отправляется при восстановлении связи. Слияние на сервере идемпотентно (у каждой записи уникальный идентификатор).
- Если два ПК были офлайн одновременно, возможен перерасход. Он не наказывается, но показывается в истории.

## 4. Защита от обхода

| Попытка обхода | Чем закрывается |
|---|---|
| Убить агент | Агент — системный сервис (root / LocalSystem); непривилегированный пользователь его не остановит |
| Убить трей | Трей только отображает; ограничения применяет сервис |
| Переименовать `java.exe`, взять другой лаунчер или портативную Java | Детект по командной строке и загруженным jar-файлам, а не по имени файла (см. 5.3) |
| Сменить часовой пояс или время | Длительность считается по тикам; сутки и окна — по UTC с поправкой, полученной от сервера, и по часовому поясу сервера |
| Выдернуть сеть | Локальный учёт продолжается; панель показывает, что устройство пропало |
| Править конфиг, журнал, токен | Файлы доступны только администратору |
| Обращаться к серверу из сети напрямую | Панель под паролем; у каждого агента свой токен; агент проверяет закреплённый сертификат сервера |
| Подделать сообщения трея | Сообщения от трея не влияют на учёт и решения |

**Вне зоны ответственности приложения** (сообщить пользователю в README):

- загрузка с флешки — нужен пароль на BIOS и запрет загрузки с USB;
- знание ребёнком пароля родительской учётки, включённый гостевой вход;
- Minecraft на телефоне, приставке, чужом ПК;
- программа, которой нет в правилах.

## 5. Архитектура

### 5.1. Компоненты

Rust workspace из четырёх крейтов. Зависимости идут только в сторону `core`; `agent`, `tray` и `server` друг от друга не зависят.

| Крейт | Тип | Роль |
|---|---|---|
| `core` | библиотека | Доменные типы, расчёт бюджета и разрешений, сопоставление правил с процессами, типы протокола. Не знает про сеть, диск и ОС |
| `agent` | бинарник `parentcontrol-agent` | Системный сервис на детском ПК: сканирует процессы, считает время, закрывает программы, синхронизируется с сервером, обслуживает трей |
| `tray` | бинарник `parentcontrol-tray` | Процесс в сессии ребёнка: иконка, уведомления, мягкое закрытие окон на Windows |
| `server` | бинарник `parentcontrol-server` | HTTP API для агентов, веб-панель, хранилище |

Рекомендуемые технологии (можно заменить при обоснованной причине): `tokio`, `axum`, SQLite, серверный HTML-шаблонизатор без отдельной сборки фронтенда, `thiserror`, `windows-service`, `notify-rust`, `ksni` или `tray-icon`.

### 5.2. Агент

- **Цикл**: каждые 5 секунд получает список процессов (PID, владелец, путь, командная строка), сопоставляет с правилами, обновляет учёт, принимает решения.
- **Учёт по тикам**: к использованию прибавляется время с прошлого тика, но не больше двух интервалов. Так сон компьютера и зависания не превращаются в игровое время.
- **Единственный источник истины для решений — локальный снимок политики** на диске: правила, недельное расписание, остаток, блокировки, поправка времени. Синхронизация с сервером только обновляет снимок. Поэтому онлайн и офлайн работают одним и тем же кодом, а на первом этапе снимок можно положить вручную.
- **Журнал использования** сбрасывается на диск не реже раза в 30 секунд и переживает перезагрузку.
- **Связь с сервером**: постоянное соединение (рекомендуется WebSocket), чтобы бонус и блокировка применялись за секунды. Агент шлёт использование, список локальных пользователей и признак жизни; сервер шлёт обновлённый снимок политики.
- **Платформенный слой** — один trait с двумя реализациями (`platform/linux.rs`, `platform/windows.rs`): список процессов, завершение процесса, список пользователей, канал связи с треем.
- **Связь с треем**: Unix-сокет на Linux, именованный канал на Windows. Агент отправляет состояние и события; от трея принимает только подтверждения доставки.

### 5.3. Детект Minecraft Java

Игровой процесс — это JVM. Лаунчер (официальный или окно Prism) игрой не считается.

Процесс считается Minecraft, если выполняется любое из условий:

1. В командной строке есть известный главный класс: `net.minecraft.client.main.Main`, `net.minecraft.launchwrapper.Launch`, классы загрузчиков Fabric / Quilt / Forge / NeoForge, точка входа Prism/MultiMC (`org.prismlauncher.EntryPoint`, `org.multimc.EntryPoint`).
2. В classpath или аргументах есть характерные признаки: путь к клиентскому jar Minecraft, `--assetsDir`, `--gameDir`, `--accessToken`.
3. Запасной слой: среди открытых или отображённых в память файлов процесса есть клиентский jar Minecraft (Linux: `/proc/<pid>/maps`, `/proc/<pid>/fd`).

Списки выше — исходные. Точные значения нужно снять с реальных запусков и сохранить как тестовые фикстуры (см. раздел 9).

### 5.4. Закрытие программ

- **Linux**: `SIGTERM` всем процессам группы, через 30 секунд `SIGKILL` оставшимся.
- **Windows**: сервис не может послать сообщение окну в сессии пользователя, поэтому мягкое закрытие (`WM_CLOSE`) выполняет трей по запросу агента. Если трея нет или процесс жив через 30 секунд, сервис вызывает `TerminateProcess`.

### 5.5. Сервер

- Один бинарник со встроенными шаблонами и статикой; данные в SQLite.
- Конфигурация: адрес и порт, каталог данных, часовой пояс, время начала суток.
- **Вход родителя**: пароль (хеш Argon2), сессионная cookie. Первый пароль задаётся командой `parentcontrol-server set-password` (на сервере: `docker compose run --rm server set-password`), а не через веб, чтобы ребёнок не опередил.
- **Подключение агента**: родитель создаёт устройство в панели и получает одноразовый код. На ПК от имени администратора выполняется `parentcontrol-agent enroll --server <url> --code <код>`. Агент получает постоянный токен и запоминает отпечаток сертификата сервера.
- **TLS**: при первом запуске сервер создаёт самоподписанный сертификат; в конфиге можно указать свой.

### 5.6. Модель данных (ориентир)

- `Profile` — ребёнок.
- `Group` — принадлежит профилю; название.
- `Rule` — принадлежит группе; встроенный профиль или свой матчер.
- `Schedule` — на группу и день недели: квота и список окон.
- `Device` — имя, платформа, токен, время последней связи.
- `AccountBinding` — устройство, имя пользователя ОС, профиль.
- `UsageRecord` — уникальный идентификатор, устройство, группа, начало, длительность.
- `Adjustment` — группа, бюджетные сутки, минуты со знаком: родитель добавляет или забирает время.
- `Block` — группа, время установки.
- `ParentAction` — журнал действий родителя.

### 5.7. Установка

- **Сервер**: Docker Compose на `192.168.1.135` под пользователем `quantick`. Docker там уже установлен, `quantick` входит в группу `docker` (подтверждено пользователем), `sudo` для развёртывания не нужен.
  - В репозитории: многоэтапный `Dockerfile` (сборка, затем минимальный образ со статическим бинарником) и `compose.yaml` в каталоге `deploy/`.
  - Один сервис `server`; `restart: unless-stopped`; healthcheck.
  - Данные (SQLite, сертификат, конфиг) — в именованном томе или каталоге в домашней папке `quantick`; они должны переживать пересоздание контейнера и обновление образа.
  - Процесс в контейнере работает не от root; права на каталог данных согласованы с этим пользователем.
  - Порт публикуется на адрес `192.168.1.135`, а не на все интерфейсы. Порт по умолчанию — `8443`.
  - Часовой пояс задаётся в конфиге сервера явно, а не берётся из контейнера.
  - Агенты подключаются по адресу `https://192.168.1.135:8443`; он же указывается в `enroll`.
  - Развёртывание — команда `just deploy` (копирование по SSH на `quantick@192.168.1.135` и `docker compose up -d --build`). Запускать её можно только с явного согласия пользователя: это действие на чужой для сессии машине.
- **Агент и трей на Linux**: статические бинарники (musl), systemd-юнит агента с ограничениями доступа, XDG-автозапуск трея. Отдельно `flake.nix`: пакеты, dev-shell, модуль NixOS для агента. Без Nix всё должно ставиться так же полноценно.
- **Windows**: команда `parentcontrol-agent install` регистрирует сервис (автозапуск, перезапуск при сбое), кладёт данные в `C:\ProgramData\ParentControl` с доступом только для администраторов и SYSTEM, прописывает автозапуск трея для всех пользователей.

## 6. Требования к качеству кода

Пользователь отдельно потребовал, чтобы кодовая база была «вылизана». Это требование наравне с функциональными.

**Структура**
- Один файл — одна ответственность; ориентир до 300 строк.
- Платформенный код только в `platform/`; в остальном коде нет `#[cfg(windows)]` и `#[cfg(unix)]`.
- `core` получает время и список процессов через trait-ы и тестируется без реальной системы.

**Типы**
- Доменные значения имеют собственные типы (`Minutes`, `GroupId`, `DeviceId`, `TimeWindow`), а не голые числа и строки.
- Невалидные состояния не создаются: проверки в конструкторах.
- Ошибки типизированы в библиотечном коде; `anyhow` допустим только в `main`.
- `unwrap` и `expect` вне тестов — только для доказуемых инвариантов, с комментарием.

**Автоматические проверки**
- `rustfmt`; `clippy` с `pedantic`, предупреждения — ошибки.
- `unsafe` запрещён вне `platform/`; там каждый блок с комментарием `SAFETY`.
- `cargo deny` для лицензий и уязвимостей.
- Всё запускается одной командой `just check` и pre-commit хуком; версии инструментов фиксирует dev-shell.
- Код под Windows должен хотя бы собираться кросс-компиляцией в `just check`.

**Тесты**
- Логика бюджета (квоты, окна, бонусы, блокировки, граница суток, офлайн-слияние) покрыта юнит-тестами и property-тестами.
- Детект Minecraft проверяется на фикстурах реальных командных строк.
- Протокол агент–сервер — интеграционным тестом с настоящим сервером в процессе.

**Гигиена**
- Нет мёртвого кода, закомментированных кусков, `TODO` без причины.
- Комментарии объясняют «почему»; у публичных элементов `core` есть doc-комментарии.
- Зависимостей минимум, каждая обоснована.
- Коммиты атомарные, с осмысленными сообщениями. Коммитить только с согласия пользователя.

## 7. Этапы

Каждый этап заканчивается зелёным `just check` и показом результата пользователю.

**Этап 0. Каркас.**
`git init`, workspace с четырьмя пустыми крейтами и границами модулей, линтеры, `cargo deny`, `justfile`, pre-commit, `flake.nix` с dev-shell.
*Готово, когда:* `just check` проходит на пустом каркасе, включая сборку под Windows.

**Этап 1. Ядро и агент на Linux.**
Доменные типы и расчёт бюджета в `core`; детект Minecraft; агент работает от локального снимка политики, считает время, предупреждает в лог и закрывает процесс.
*Готово, когда:* на Linux Minecraft из официального лаунчера и из Prism закрывается по исчерпании квоты и вне окна, повторный запуск пресекается, учёт переживает перезапуск агента.

**Этап 2. Сервер и панель.**
Хранилище, вход родителя, подключение агента, синхронизация, все разделы панели, офлайн-слияние, `Dockerfile` и `compose.yaml`.
*Готово, когда:* сервер поднимается через `docker compose up` и данные переживают пересоздание контейнера; бонус и блокировка из панели применяются на ПК за секунды; после отключения сети агент продолжает ограничивать, а после восстановления история сходится.

**Этап 3. Агент на Windows.**
Реализация платформенного слоя, сервис, команда установки.
*Готово, когда:* сценарии этапа 1 проходят на Windows под учёткой без прав администратора, и эта учётка не может остановить сервис или изменить его файлы.

**Этап 4. Трей и уведомления.**
Иконка с остатком, предупреждения за 10/5/1 минуту, причина закрытия, мягкое закрытие окна на Windows.
*Готово, когда:* ребёнок видит остаток и предупреждения на обеих ОС; завершение трея не влияет на ограничения.

**Этап 5. Упаковка и документация.**
Systemd-юнит и модуль NixOS для агента, `just deploy` для сервера, README с развёртыванием сервера, установкой агента на обе ОС и списком того, что приложение не закрывает (раздел 4).
*Готово, когда:* установка на чистую машину проходит по README без правки кода.

Проверить Windows из Linux-сессии нельзя. Для этапов 3 и 4 нужно дать пользователю чек-лист ручной проверки и получить от него результат.

## 8. Чего не делаем

- Bedrock Edition, мобильные устройства, приставки.
- Белый список программ; лимит на весь компьютер или блокировка сессии.
- Запрос дополнительного времени со стороны ребёнка.
- Доступ к панели из интернета, Telegram-бот, уведомления родителю.
- Интерфейс для нескольких детей (модель данных их допускает).
- Учёт по активному окну или простою ввода.

## 9. Что нужно проверить на практике

1. Успевает ли Minecraft сохранить мир при `SIGTERM` на Linux и при `WM_CLOSE` на Windows за 30 секунд. Если нет — пересмотреть способ мягкого закрытия.
2. Реальные командные строки игры при запуске из официального лаунчера и из Prism (в том числе Flatpak-версии) на обеих ОС; уточнить по ним списки из 5.3 и собрать фикстуры.
3. Как надёжно получить список загруженных jar-файлов процесса на Windows для запасного слоя детекта.
4. Может ли непривилегированный пользователь Windows изменить системное время в конфигурации пользователя; если да — учесть в защите.

## 10. Решения по умолчанию, не обсуждавшиеся с пользователем

Их стоит подтвердить у пользователя, прежде чем на них опираться:

- Корректировка меняет только квоту и не отменяет окно: вне окна играть нельзя даже с добавленным временем.
- Блокировка бессрочная, до ручного снятия.
- Интервал сканирования 5 секунд; запрещённый запуск пресекается в пределах этого интервала.
- Первый пароль панели задаётся из командной строки сервера.
- Самоподписанный сертификат по умолчанию (браузер родителя покажет предупреждение).
- Интерфейс на русском, код на английском.
- На Windows установка командой агента, без MSI.
- Порт сервера `8443`; данные контейнера лежат в томе Docker.
